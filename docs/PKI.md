# RivetHub PKI: holder-generated keys, CSR signing, short-lived certificates

Approved 2026-10-14.
This supersedes the CA parts of DESIGN-2026-10-12 ("certificate authority commands over rcgen" in cli) and CONTRACT B14's
"CA layout under the legacy shared CA directory" as the target. rivet-ca.sh's on-disk layout is read once, at import.

## What is wrong today
- 21 private keys, 3 .p12 bundles and the intermediate's key sit on NFS (`the legacy shared CA directory/issued`, `intermediate/`),
  readable by every node as user rivet.
- Device keys are generated by the issuer and shipped as PKCS#12.
- Identity is a CN string (`device:…`, `node-a`, `grok@node-b`). Renewal is manual, every 90 days.

## Target
1. **Keys are born on the holder and never leave it.** Nodes, agents and devices generate an ECDSA P-256 key locally and
   send a CSR. The CA signs it. Nothing ever sends or stores a private key on its behalf. There is no PKCS#12.
2. **Identity is a SPIFFE URI SAN**, verified by the TLS stack, never parsed from a CN:
   - `spiffe://rivet.mesh/node/<node>`
   - `spiffe://rivet.mesh/agent/<node>/<agent>`
   - `spiffe://rivet.mesh/device/<user>/<device>`
   The gateway's TLS verifier turns a verified chain into one typed `Principal { Node, Agent, Device }`. Authorization is one
   policy table keyed by principal kind, and refusal is the default. During migration only, a legacy leaf (CN `device:*` /
   OU `client`, chained to the same root) maps to `Device` through the users registry, with a deprecation log line.
3. **Short-lived certificates with automatic renewal.** Nodes and agents get 7 days and devices 30 days. Holders renew at
   two-thirds of lifetime with a new CSR signed by their current certificate (mTLS to the CA). There is no manual
   90-day cycle.
4. **The CA is a service on the datahub, and its keys never leave it.** The intermediate key lives only in the CA
   service's state dir (0600, not on NFS). The root key is offline: it is imported once, used to sign the intermediate,
   then exported to the operator and deleted from the host.
   HTTP, TLS, on the gateway's listener under `/ca/v1/`:
   - `POST /ca/v1/sign`: accepts a CSR plus either a one-time enrollment token (first issue) or the caller's current
     valid cert (renewal). Requested SANs must match what the token or current identity allows; anything else is refused.
   - `GET /ca/v1/chain`: the intermediate and root, PEM.
   - `GET /ca/v1/crl`: the current CRL, a standard X.509 CRL, also written to the same path as today so TypeScript
     nodes keep reading it during cutover.
   - Enrollment tokens: one-time, short TTL (15 min), bound to one principal, CSPRNG, stored hashed, compared in constant
     time. Issuing and signing are rate-limited.
5. **Revocation:** `rh ca revoke <principal|serial>` updates the CRL, and every TLS verifier checks it. Short lifetimes
   bound the exposure if a check is missed.
6. **Crates:** a new `pki` crate (adapter layer, depends on kernel and wire only) for CSR validation, SAN policy,
   signing, the CRL, the import of rivet-ca.sh's index.txt/serial, and lifetimes. It uses `rcgen`, `rustls-webpki`,
   `x509-parser` and `rustls-pemfile`; no hand-rolled ASN.1 or PEM. A kernel port `CertificateAuthority` (sign, chain, crl,
   revoke, issue_token) is implemented by `pki` and injected by the composition root. The gateway serves `/ca/v1/*`
   and the device enrollment routes through that port. `rh ca …` commands (init/import, token, revoke, crl, status) and
   `rh cert renew` (the holder side: keygen, CSR, renewal loop) live in cli.

The CA takes node names from the operator roster and never from `/mesh.json`, because that registry is self-registered.

## Migration (no flag day)
1. `rh ca import` reads rivet-ca.sh's root/intermediate and index.txt once. Existing certificates stay valid until
   they expire (same chain).
2. Nodes switch to `rh cert renew` and hold SPIFFE certs within one renewal period.
3. Devices re-enroll with a token: the desktop and Android apps must generate a key and CSR. That is an app change in
   the RivetHub apps, outside this runtime. Until it ships, legacy device certs keep working through the legacy mapping.
4. After every holder has re-enrolled: retire rivet-ca.sh, delete `issued/*.key` and `*.p12` from the share, and drop
   the legacy CN mapping.

## Contract change (B14)
B14's CA row becomes: the `/ca/v1/` API above, SPIFFE URI SAN identities, a standard CRL at the existing path, and
rivet-ca.sh's layout read once at import. The CONTRACT and ARCHITECTURE docs are updated by the first PKI slice.

## The kernel port (exact shape; both the pki slice and gateway slices use this)
```rust
// crates/kernel/src/ca.rs
pub struct CsrPem(pub String);
pub struct CertChainPem { pub leaf: String, pub chain: Vec<String> }
pub struct CrlPem(pub String);
pub enum Principal { Node { node: String }, Agent { node: String, agent: String }, Device { user: String, device: String } }
pub struct EnrollmentToken(pub String);           // secret; Debug must not print it
pub enum SignAuthority { Token(EnrollmentToken), Renewal(Principal) } // Renewal = the caller's verified current identity
#[derive(Debug, thiserror::Error)] pub enum CaError { Refused(String), InvalidCsr(String), Unavailable(#[source] BoxError) }
#[async_trait] pub trait CertificateAuthority: Send + Sync {
    async fn issue_token(&self, principal: Principal) -> Result<EnrollmentToken, CaError>;
    async fn sign(&self, csr: CsrPem, authority: SignAuthority) -> Result<CertChainPem, CaError>;
    async fn chain(&self) -> Result<Vec<String>, CaError>;
    async fn crl(&self) -> Result<CrlPem, CaError>;
    async fn revoke(&self, principal: Principal) -> Result<(), CaError>;
}
```
Whichever slice lands first adds it to kernel exactly like this. The other rebases onto it.
